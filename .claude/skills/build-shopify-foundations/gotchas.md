# build-shopify-foundations — gotchas

(Theme-write / mapping gotchas accumulate here; this file is injected at the top of SKILL.md each run.)

- 2026-06-10: `config/settings_data.json` is **JSONC** — it opens with a `/* auto-generated */` header. Strip it before `JSON.parse` (use `safe-shopify-write.js` `parseSettingsData`) and re-prepend it on write (`settingsDataHeader`), or the theme-editor banner is lost.
- 2026-06-10: Horizon color roles are all `"alpha": true`, so Aristopet alpha colors (`#rrggbbaa`, `rgba(0,0,0,0)`) write directly — do NOT strip alpha.
- 2026-06-10: the host (crunchy-horizon) is at the repo root and `config.themeRoot` is `"."` — resolve theme paths relative to the repo root.
- 2026-06-10 (live run): **`settings_schema.json` is CRLF + hand-mixed formatting — do NOT reserialize the whole schema.** `JSON.stringify(schema,null,2)` emits LF + uniform indentation, but the host file uses `\r\n` and inlines *some* option arrays (font-source selects) while expanding others (sizes). A full reserialize rewrites nearly every line (huge spurious diff your `theme dev` would push). For an option addition (e.g. `type_size_h1 += 80px`) do a **surgical text insert** that preserves bytes. `settings_data.json` is LF and round-trips faithfully, so reserializing it (with the JSONC header re-prepended) is fine. `applyPlan`'s reserialized schema is correct as *data* but must not be written verbatim.
- 2026-06-10 (live run): **Round-trip the BEFORE file through your serializer and assert it equals the original, before writing.** `recon(beforeData) === originalText`? If not, your write will reformat the file — switch to a surgical edit. This single check caught the CRLF + inline-array drift on the schema here.
- 2026-06-10 (live run): **Detect font availability empirically on the live `:9292` preview — don't ask the developer.** `document.fonts.check('700 24px "Instrument Sans"')` plus the `:root` `--font-heading--family` var confirm the font actually loaded (vs fell back to `sans-serif`). Verified Instrument Sans 700 + DM Sans 400/600 loaded this way; the warm palette via `--color-background/foreground/primary` (`#fffefd / #2a2620 / #af7d4f`).
- 2026-06-11 — **Heading fonts may diverge BY LEVEL, but the manifest currently collapses them — surface it as a gap (the real fix is upstream extraction).** The design uses Instrument Sans for display H1–H3 but **DM Sans SemiBold for H4–H6 / product titles**, yet `foundations.typography.presets` assigns **every** `h1..h6` `fontRole:"heading"` — so the per-level font divergence is lost at EXTRACTION (`/analyze-theme`), before this skill runs. Downstream consequence (surfaced building a product-list): a component's `type_preset: h5` gets the right SIZE (20px) but the wrong FONT (Instrument Sans, not the design's DM Sans). Until extraction assigns `fontRole` per level by the actual Figma font, this skill cannot write per-level heading fonts faithfully — flag a `heading-font-divergence` gap instead of silently shipping one heading font for all levels. (Roadmap F24b; same typography/role machinery that element-foundations uses for `button_font`.)
