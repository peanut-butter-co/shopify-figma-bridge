This directory is **both** the real Aristopet **handoff** and the **frozen golden fixture** that SP-2
(`/build-shopify-foundations`) is built and validated against. It was produced by **SP-1 (AI inference)**
because Aristopet was designed off-process on an older skill-pack version and never emitted these
deliverables. It is validated by the `SP-1: Aristopet inference artifact set` group in
`.claude/scripts/skills-tests.js`.

> **SP-1.1 recompute (current state).** `design-rules.json` + `work-order.json` were **recomputed against
> the real host, crunchy-horizon** (a rich Horizon fork at the repo root, `themeRoot:"."`), replacing

> design facts. Regenerated by `.claude/scripts/recompute-aristopet.js`; the fuzzy candidate-matches live

## Reachability outcome (honest) — SP-1.1 against crunchy-horizon

The host is now a rich Horizon fork, so **15 / 22 sections have a host candidate → `config` baseline**
(e.g. `footer`→`footer`, `marquee`→`marquee`, `header-v1/v2`→`header`, `related-products`→`product-recommendations`),
and **6 stay `code`/`no-candidate`** (truly bespoke: `trust-bar`, `ugc-captions-below`, `newsletter-signup`,
`collection-header`, `filter-bar`, `pagination`); `product-reviews` → **app**. **Bias-to-code still holds at
the work-order level:** Aristopet's off-process setting vocabulary (`left_title`, `menu_item_1`, …) is not
Horizon's, so every `config` component still routes to code via a **`value-out-of-domain` delta**
("host section exists; re-author its settings to the host schema" — SP-3's per-component job). A `config`
verdict means *"there is a Horizon section to build ON"*, not *"drop the JSON in."*
**work-order: 28 code (6 no-candidate + 19 value-out-of-domain + 3 mobile-divergence) + 1 app + 0 out-of-scope.**

## Fidelity notes (v1)

- **Settings are representative:** one `get_design_context` extract per *distinct* section, reused across
  its occurrences (e.g. the two homepage `product-card-row`s share the extracted settings).
- **Spacing wrappers folded out:** the "Section Heading" / "Section Footer" wrappers are dropped from
  `compositions`; their standalone heading texts are not captured in v1.
- **Color schemes (4)** are clustered from section backgrounds (White / Warm White / Sand / Espresso),
  confidence medium — not the full 33-role Shopify palette.
- **Chrome** (header / footer / newsletter) is kept in each composition's `order`; the
  `header-group.json` / `footer-group.json` placement is an SP-2 concern.

## Regenerate `design-rules.json` + `work-order.json` (never hand-edit)

Both are host-dependent and DERIVED. Re-resolve them against the live host (run from the repo root so
`themeRoot:"."` resolves) — this re-reads crunchy-horizon, applies `CANDIDATE_MAP`, and re-derives the
work-order, with all contract invariants as a STOP gate:

```bash
node .claude/scripts/recompute-aristopet.js          # --dry to preview counts + invariants without writing
```

To change a candidate-match (e.g. a wrong fuzzy mapping), edit `CANDIDATE_MAP` in
`.claude/scripts/recompute-aristopet.js` and re-run. `compositions` + `foundations` (in `manifest.json`)
can be regenerated from the `_raw/` captures with
`node .claude/figma-sync/aristopet/_raw/build-manifest.js`.
